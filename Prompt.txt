You are working inside our UniLumos fork.

Goal:
Run/report UniLumos official demo scenarios in the same reporting style as our Relit-LiVE BSS experiments, but with support-aware cross-model tables.

Important philosophy:
- We want a cross-model, cross-modality reporting format.
- One row should correspond to one model/protocol.
- The cross-modality main metric is `rgb_l1_closure`.
- Do not invent new demo scenarios.
- Use official UniLumos demo scenarios only.
- Do not create Cartesian products of foreground/background/prompt assets unless the official script or official manifest already specifies those combinations.
- Do not train anything.
- Do not modify weights.
- Do not change official conditioning, prompts, examples, preprocessing, sample_shift, resolution, checkpoint loading, or model architecture.
- Only change the inference schedule grid.

BSS definition:
For actual NFE T:
- Construct the official base schedule with T-2 sample steps.
- Split the first interval.
- Split the last interval.
- Run exactly T model evaluations.

Examples:
- bss10 = base8 + split first/last
- bss16 = base14 + split first/last
- bss20 = base18 + split first/last
- bss24 = base22 + split first/last

BSS-T is NOT uniform T.
BSS is teacher-free at inference.
Reference output is used only for metrics.

Reference:
For UniLumos, treat `reference_uniform25` with `sample_steps=25` and `sample_shift=8.0` as the official-default reference unless local official code shows a different default.
Do not use uniform50 as the main official reference unless explicitly instructed. If uniform50 is run, mark it as extended high-step reference.

Main comparison:
- Same-compute quality: BSS vs uniform at the same actual NFE.
- Same-quality compute saving: how many fewer NFEs BSS needs than uniform to reach the same `rgb_l1_closure`.

PHASE 7 — Generate support-aware cross-model tables
====================================================================

Create:

`bss_experiments/unilumos/scripts/make_cross_model_tables.py`

Important:
The cross-model table uses official compute fractions:

`c ∈ {0.2, 0.4, 0.6, 0.8}`

But do NOT leave empty cells in the main table.
Also do NOT extrapolate below the tested support.

Use support-aware reporting.

Support tags:
- `E`: exact target compute fraction tested.
- `I`: interpolated within tested range.
- `F`: floor. Target fraction is below the minimum valid tested NFE; report the lowest valid tested point and tag actual fraction.
- `N`: nearest tested point, only if interpolation is not appropriate but target is within support.
- `C`: ceiling. Target fraction above max tested range; only use if explicitly allowed.
- `OOS`: out of support. Avoid in main table unless no numeric value can be responsibly shown.

Default rule:
1. target_nfe = c * reference_nfe.
2. Find same-NFE pairs where both uniformT and bssT exist.
3. If exact actual NFE exists, use it and tag `E`.
4. Else if target lies inside tested range, interpolate and tag `I`.
5. Else if target is below min tested NFE, use min tested NFE, tag `F@actual_compute`.
6. Else if target is above max tested NFE, use max tested NFE only if allowed, tag `C@actual_compute`; otherwise mark OOS.
7. Do not use extrapolation in the main table.
8. Do not include `F`, `C`, or `OOS` points in Mean Δ or ΔAUC unless explicitly configured with `include_support_points=True`.

Cell display format:

`BSS_closure / +delta [TAG@actual%]`

Example:

`0.365 / +0.250 [E@40%]`

If target is 20% but lowest valid point is 40%:

`0.365 / +0.250 [F@40%]`

This means: 20% target is below support; we report the lowest valid operating point, which is 40% official compute.
